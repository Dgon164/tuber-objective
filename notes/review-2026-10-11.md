# Review of the 10-10 work: the rules that the work broke, what failed, and the method to follow

The author wrote this review on 2026-10-11 after a read of the package
from the work of 10-07 to 10-10 (`agc-test/`, `fabric-additions/`,
`HANDOFF_2026-10-11.md`). The review is in plain language. The line
numbers refer to the files in that package. The package was a work folder
on a different machine, and the package is not in this repository. The
result of the package is `examples/agc-live/`: the trace patch, the socket
client, the recordings, and the runs. The review stays as the author
wrote the review.

## 1. The short version

The emulator, the clock, the vehicle, and the socket plumbing are
correct. The autopilot of the flight program damped a nudge through the
socket. That result is real. It is recommended to keep that result.

New code did each thing that the package says the code learned. The new
code does not use `discovery.py` at all. The new code got 4 things:

- the physics as equations
- the true constants as start values
- the goal as a gauge
- a score function to minimize

Then the new code "learned" what the new code got. The goal as stated
was: understand the code, find what each part does and needs, and chain
the needs back from the goal. The new code did not try that goal.

The package gave some things on purpose, as a concession, because the
bare version is very hard. A concession is permitted. A concession must
obey 3 rules:

- You write the concession down as a given.
- The concession is the smallest thing that unblocks the work.
- The concession is never the answer.

Section 5 below shows the type of each given.

## 2. The rules, for reference

The rules come from `notes/design-rules.md`, `guides/the-process.md`, and
section 14 of the paper. The rules have numbers here so that the rest of
this note can point at the rules.

- **R1. One comparator and a memory.** Each step is "same, different,
  not part," or a count of that result.
- **R2. Define nothing.** No target, no idea of right or wrong, no
  feature list, no training step. What you tell the program to look for
  can be different from what the program must find.
- **R3. Keep all.** The program removes, prunes, filters, or retires
  nothing. A part that occurs 1 time has the same standing as a part
  that occurs 1,000 times. Compression is a count, not a removal.
- **R4. Loop until stable.** The only stop rule is a round that makes
  nothing new. No round limit, no score threshold.
- **R5. The comparator is the scorer.** Feedback is the comparator
  pointed at the output: against the memory, against the output of the
  program, or against an answer key from the user. There is no separate
  loss function (no separate "how good is this?" function).
- **R6. No checks or filters that nobody asked for.** Do not solve a
  problem before the problem occurs. Make the thing, and let the result
  surprise you. The checks are what kept the system from a stable state.
- **R7. Never treat a common part as unimportant.** Many connections
  mean that the part is important.
- **R8. The lens changes the display and nothing else.** Names, labels,
  and the format of the output are for the reader, never for the method.
- **R9. The thing stands for itself.** The documents make no claims. The
  records are the evidence.
- **R10. The user supplies the selection signal and says so.** Base
  Discovery records all structure that occurs many times. To isolate 1
  specific target needs a selection signal from the user: an answer key,
  a yes/no, or a goal row. That signal is a given that the user states,
  not a given that the user hides.

The goal, as stated on 10-10 in the morning, was: no manual, no training
step. Read the code. Read the code in operation. Find what each part does
and what each part needs. Chain the needs backward from "landed" to the
first key press.

## 4. The rules that each part broke

### pilot.py

- **R2, define nothing.** `Model.predict()` (lines 94-157) is the physics
  of the world, written directly into the pilot: the gravity law, the
  rocket equation, exponential drag, and orbit elements. The comments
  call the function "the manual". In practice, the function is a
  simulator that the author wrote. The function discovered nothing.
- **R2 again, the true constants.** `PRIORS` (line 75) are the exact
  numbers of the world: thrust 7.5 MN, planet constant 3.986e14, exhaust
  velocity 2800. The step "Measured in flight" fits 5 constants again,
  with the answer as the start point.
- **R10, an answer that is hidden.** `gauges()` (line 191) gives the
  apogee and the perigee (the high point and the low point of the
  orbit). The `orbit()` function of the world computes the apogee and
  the perigee. The goal is "apogee = perigee = 200 km." The pilot reads
  the score from the world. The package did not write this gauge down as
  a given.
- **R5, a separate scorer.** `orbit_error()` (line 310) is a loss
  function that the author made by hand. `plan()` (lines 337-367) does a
  grid search over schedule values that the author selected by hand, to
  minimize the loss. The author wrote `throttle_rule()` and
  `cutoff_rule()`. The program did not find them.
- **R9, the claim.** The claim "Inserts into orbit within a few km of
  what it predicted" describes a simulator. The simulator agrees with a
  world made from the same equations and constants. The record shows that the pilot
  copied. The record does not show that the pilot learned.
- **The goal.** The AGC is not in the loop. `pilot.py` flies
  `fly.World`, a Python toy. The author recorded the flight computer and
  then did not use the recording.

### fly.py

- **R10, an answer that is hidden.** `calibrate()` (lines 294-325)
  computes the pitch schedule, the launch window, the lead angles, and
  the deorbit point from the true physics constants. The function writes
  these values into the target values of the plan. Then the score of the
  learner is how close the learner comes to those targets. The plan is
  the answer, and the package does not state this fact.
- **R5, a separate scorer.** `Learner.cost()` is a weighted squared error
  against the targets. The author selected the weights and the
  tolerances for each instrument by hand. The learner selects the action
  with the lowest cost that the learner predicts. That is a training
  step to fly.
- **R2.** `LABELS` tells the learner the switch that each button sets.
  This given is small, but it is a given.
- **The goal.** There is no AGC. The entry in the log (10-10, late) lists
  5 reasons for the failure. The reasons are reasons that a controller
  that a reward drives fails. The reasons are not reasons that Discovery
  fails, because the package never ran Discovery.

### room.py / lookback.py

These scripts are the closest to the spirit of the rules: the scripts
compare, cycle, and keep a memory. But the scripts break these rules:

- **R6 and R7, a filter at the front.** `unexpected()` (line 84) keeps an
  overlap only if data in random order reaches the overlap less than 1
  time in 20. The filter removes common overlaps and weak overlaps
  before the overlaps can interact with anything.
- **R3, deletion.** The retire step: if the world refuses the words that
  an overlap made 3 times, the overlap "stops being used." The log says
  that cycle 3 got worse, and the author added the retire step to
  correct that problem. R6 says that this is the wrong direction. The
  retire step is a correction for a problem that the first check caused.
- **R10, an answer that is hidden.** The "world" is a dictionary of the
  same root families that the seed came from. The author confirmed the
  "13 real words built" with a question to the world. The world is an
  answer key, and the author made the world from the answer. An answer
  key is permitted if the author states the answer key. The docstring
  states the answer key, so the world is a given that the author
  declared. That is permitted. But the author must count the world as a
  given.
- **R2, small.** The feature is letter triples. The author made `sh` and
  `kh` into 1 letter. That is language knowledge, given to the program.
- **lookback.py, R3 again.** The script mints "filters" from yes/no paths
  and does not make a word when a filter holds. To mint a part is to
  make a new part from 2 parts that have the same start or the same end.
  A filter that the script mints from the signal is closer to the rules
  than a filter that the author writes by hand. But the filter still
  removes. The rules say sort, do not skip: make the word, record the
  no, and keep both.

### effects.py, decisions.py, schedule.py

- **R2, a feature list.** `change_fact()` and `where_fact()` (lines
  67-85) list "up one," "down one," "to zero," "from zero," "tail10
  matches." These functions specify what an effect looks like before the
  search for an effect. The feature "tail10 matches" is knowledge of the
  10-bit address field of the AGC.
- **R6, thresholds.** The thresholds are 90 percent to count as a
  signature, groups of 3 or more, and a 100 ms window before a jet
  fires. Each threshold is a cutoff that decides what counts.
- **R8, correct.** The scripts use names only in the output. This is
  correct.

These scripts are satisfactory aids to read the traces. The scripts are
not Discovery. Do not present the scripts next to Discovery as if the
scripts were Discovery.

## 5. Givens: the permitted givens, the stated givens, and the givens that were the answer

A given is permitted when the given obeys 3 conditions:

- (a) The author writes the given down as a given.
- (b) The given is the smallest thing that unblocks the work.
- (c) The given is not the answer.

The separator rule, the frame rule, and the cap are givens in Discovery
itself. The file `notes/design-rules.md` now lists these 3 givens as
givens.

| given | place | in writing | the smallest | the answer |
|---|---|---|---|---|
| the goal state (orbit at 200 km, or "landed") | pilot.py `WAYPOINT`, fly.py plan | partly | yes | no. The goal state is the selection signal of R10, and R10 permits the goal state. |
| a flight plan (the shape of the trajectory: up, tip over, stage, burn until the orbit gauges read the target) | pilot.py `PLAN`, fly.py `make_plan()` | yes, in the docstring | no. See below. | partly |
| the physics as equations | pilot.py `Model.predict()` | the package calls this given "the manual" | no | **yes** |
| the true constants | pilot.py `PRIORS` | the package calls this given "the plan's numbers" | no | **yes** |
| the apogee gauge and the perigee gauge that the world computes | pilot.py `gauges()` | no | no | **yes** |
| a score function | pilot.py `orbit_error()`, fly.py `cost()` | no | no | **yes**. The score function is the idea of right and wrong that R2 forbids. |
| the target values of the plan that come from the true constants | fly.py `calibrate()` | no | no | **yes** |
| panel labels (the switch that each button sets) | fly.py `LABELS` | yes | yes | no |
| an oracle dictionary | room.py `WORLD` | yes | yes | the oracle dictionary is the answer key. The author declared the answer key, so R10 permits the answer key. |
| letter triples, `sh`/`kh` as 1 letter | room.py | yes | not certain | no |

**The flight plan concession.** A flight plan can be a given. The form
of the flight plan is important. The flight plan of the Apollo crew was
a list of DSKY entries and the times to make each entry. A DSKY entry is
a key press on the keyboard of the spacecraft. That flight plan is a procedure, not
physics.

A concession of that kind is: "here are the programs in order: P63, P64,
P66; start each when the display shows the previous one is done." A
concession of that kind unblocks the key-press problem, and gives no
physics, no constants, and no scores. Instead, the package gave the
mission control side of the plan. That side contains 3 things: the
numbers that make the plan, the equations behind the numbers, and the
gauges that report the result.
That is the answer in the form of a plan.

If you want a clean list of concessions for this experiment, the list
is:

1. The goal row: the telemetry that a landing shows. (R10 permits this
   given.)
2. The DSKY key vocabulary. Or let the program find the vocabulary from
   OPR ERR (the error that you get when you press the wrong keys). Both
   options are permitted, and the second option costs little.
3. As an option, the program order as the crew had the order. State the
   order as a given.

Nothing else. No physics, no constants, no gauges that the world computes
from its internal values, and no cost function.

## 6. The method to follow

The author wrote this method down on 10-10 in the morning, in chat and
in `notes/open.md` under "The AGC in the loop." This section states the
method again, with what each step makes and what you must never give to
the program.

**Step 0. The code as a file.** This step is complete, in
`examples/agc/`. The step found the word size, the instruction
vocabulary, and `TC BANKCALL` with its targets. The author gave nothing
to the program.

**Step 1. Opcodes by effect.** The signal is the write trace, with 1
record for each write: the instruction word, the address, the old value,
and the new value. Run `discovery.py` on the write trace. The mint groups
the records that share structure. The classes group the instruction words
by the changes that the words make. Writers, counters, flags, and the
opcode bits that decide each come out as classes. The opcode bits are the
part of the instruction that says what to do. If the classes do not come
out, the absence is a result, and the record shows the absence. The
author gives nothing: no "up one," no "tail matches," no threshold.

**Step 2. The read set and the write set of each subroutine.** Cut the
trace at the subroutine boundaries that the step-0 record already has.
To cut is to divide a signal into runs at a separator. A subroutine is a
block of code that does 1 job. The write set of each stretch is the
addresses that the stretch wrote. The read set of each stretch is the
addresses that the stretch loaded before each branch. The read set comes
from the instruction words, after step 1 has grouped the loads and the
branches. Match the read set of 1 routine against the write set of each
other routine. That match is the comparator on 2 sets, the same as
`bridge.py`. The run order of the routines comes out of what each routine
needs. The author gives nothing.

**Step 3. The code against the vehicle.** The signal is the 3 recordings
from 1 flight, on the same clock: `writes.bin`, `channels.bin`, and
`vehicle.bin`. Run Discovery on each recording. Bridge the 3 records
(find what the records share). The bridge finds the cells of the erasable
memory, the channel bits, and the vehicle rows that share structure. The
vehicle (`vehicle.py`) is the simulation, and the vehicle can know
physics. The learner never sees inside the vehicle. The author gives
nothing, except the simulation.

**Step 4. The walk backward.** The given is the goal row (R10). From the
goal row, find the channel states that come with motion toward the goal
row. Then find the routines that write those channels. Then find the
routines that those routines need. Then find the keys that start those
routines. The walk is a walk with many hops through the record. Each hop
is the comparator, with the question "is this the node I'm looking for".
If the walk does not reach a key, the record says where the walk stopped.
That point is the result.

**Step 5. Press the keys that the walk found.** The script `channel.py`
presses the keys. The vehicle moves, or the vehicle does not move. Record
the result. Compare the final telemetry with the goal row. The difference
goes back in as the next signal. There is no reward, no cost, and no new
plan: the comparison is the feedback (R5).

At no step does the author give these things:

- equations
- constants
- a simulator that the learner can run
- gauges that the world computes from its internal values
- a score function
- a feature list
- a threshold

These things make the method hard, and the rules permit the method to
stay hard:

- Step 1 can fail to give clean opcode classes on the first try. The
  record decides.
- Step 2 is not exact where the AGC uses indexed addressing. The trace
  fills the gap.
- Step 4 can stop before a key. That stop is the result.

The answer corrects none of these problems. More signal, a different cut,
or a second separator corrects these problems. The rules permit those
corrections.

## 7. The parts to keep and the parts to remove

Keep these parts:

- the clock patch
- `agctrace.py`
- `vehicle.py`
- `run_vehicle.sh`
- `channel.py`
- `build.sh`
- `run.sh`
- `symtab.py`/`names.txt` as a lens
- the recordings
- the result of the flight with the hold (the autopilot caught the nudge,
  and the real code closed the loop through the socket)

Remove from the repository: `fly.py`, `pilot.py`, and their logs. These
files are not Discovery, and a reader will think that these files are
Discovery. If you want the record of the try, keep these files in a
different place.

Keep separate: `room.py` and `lookback.py` are their own experiment. If
you keep these scripts, do 3 steps:

1. Remove the chance cutoff and the retire step.
2. Keep each thing with its counts.
3. Run the scripts again.

The thing to find out is if cycle 3 becomes stable without the checks.

Rewrite `effects.py`, `decisions.py`, and `schedule.py` as readers only,
and say so in their headers. Or replace the categories that the author
designed with a Discovery run on the same records, and compare what each
finds.

Then do step 1. The write trace exists. `discovery.py` exists. The run is
1 line. The record shows if the method works on this signal.
