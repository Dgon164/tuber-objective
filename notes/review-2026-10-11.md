# Review of the 10-10 work: which rules it broke, what failed, and how to do it instead

The author wrote this review on 2026-10-11 after reading the package of
work from 10-07 to 10-10 (`agc-test/`, `fabric-additions/`,
`HANDOFF_2026-10-11.md`). The package was a working folder on a
different machine, and it is not in this repository. Its subject was the
Apollo 11 flight program: running it on an emulator (a program that
imitates the original Apollo Guidance Computer, the AGC), connecting
that emulator to a simulated vehicle, and trying to find, from the
running program alone, how to fly it. What came out of the package is
`examples/agc-live/`: the trace patch (the change to the emulator that
records what the flight program does), the socket client (the script
that connects to the running emulator and presses keys), the recordings,
and the runs. The review is in plain language, and the line numbers
refer to the files in the package. The text is kept as the author wrote
it that day.

## 1. The short version

The emulator, the clock (a counter that stamps every recorded event with
the machine's own step count), the simulated vehicle, and the connection
code that joins them all work. The flight program's autopilot, the part
of the program that keeps the vehicle pointed the right way by firing
small jets, felt a nudge arrive through that connection and damped it
out. That result is real. Keep it.

Everything else the package says it "learned", new code did, and that
new code does not use `discovery.py` at all. Discovery, the program in
`discovery.py`, finds the structure of any file by comparing pieces of
it with each other, and it is handed nothing else. The new code was
handed four things:

- the physics, as equations
- the true constants, as starting values
- the goal, as a gauge: a readout the simulated world computes that
  says how close the vehicle is to the goal
- a score function to minimize: a formula that turns the gap from the
  goal into one number

Then it "learned" what it had been handed. The goal as stated was:
understand the code, find what each part does and what it needs, and
chain those needs backward from the goal. The new code never tried that.

The package handed some of this over on purpose, as a concession,
because the bare version of the problem is very hard. A concession is
allowed. It has to obey three rules:

- You write it down as a given, a thing the program was handed rather
  than found.
- It's the smallest thing that unblocks the work.
- It's never the answer.

Section 5 below sorts each given by those rules.

## 2. The rules, for reference

The rules come from `notes/design-rules.md`, `guides/the-process.md`,
and section 14 of the paper. They're numbered here so the rest of this
note can point at them.

- **R1. One comparator and a memory.** The comparator is the one
  operation Discovery has: take two things and sort their contents into
  what's the same, what's different, and what wasn't touched. The memory
  keeps what earlier comparisons found. Every step of the program is
  that comparison, or a count of its answers.
- **R2. Define nothing.** No target, no idea of right or wrong, no list
  of features to look for, no training step. What you'd tell the program
  to look for can differ from what it needs to find.
- **R3. Keep everything.** The program removes, prunes, filters, or
  retires nothing. A part seen once counts as much as a part seen 1,000
  times. Compressing means storing a thing once with a count beside it,
  not throwing anything away.
- **R4. Loop until stable.** The only reason to stop is a round that
  makes nothing new. No round limit, no score threshold.
- **R5. The comparator is the scorer.** Feedback is the same comparison
  pointed at the output: against the memory, against the program's own
  output, or against an answer key the user supplies. There is no
  separate "how good is this?" function.
- **R6. No checks or filters nobody asked for.** Don't solve a problem
  before it happens. Build the thing and let the result surprise you.
  The checks are what kept the system from settling into a stable state.
- **R7. Never treat a common part as unimportant.** Many connections
  mean a part matters.
- **R8. The lens changes the display and nothing else.** A lens is how
  the record prints things for people to read. Names, labels, and the
  format of the output are for the reader, never for the method.
- **R9. The thing stands for itself.** The documents make no claims.
  The records the program writes are the evidence.
- **R10. The user supplies the selection signal and says so.** Plain
  Discovery records every structure that occurs more than once. To
  single out one target, the user has to supply a selection signal, a
  way of saying which outcome counts: an answer key, a yes/no, or a goal
  row (the readings the vehicle should show when the goal is reached).
  That signal is a given the user states, not one they hide.

The goal, as stated on the morning of 10-10, was: no manual, no training
step. Read the code. Read the code as it runs. Find what each part does
and what each part needs. Chain the needs backward from "landed" to the
first key press.

## 4. Which rules each part broke

### pilot.py

- **R2, define nothing.** `Model.predict()` (lines 94-157) is the
  physics of the world written straight into the pilot: the law of
  gravity, the rocket equation, exponential drag, and the elements that
  describe an orbit. The comments call it "the manual". In practice it
  is a simulator the author wrote. It discovered nothing.
- **R2 again, the true constants.** `PRIORS` (line 75) are the exact
  numbers of the world: thrust 7.5 MN, planet constant 3.986e14, exhaust
  velocity 2800. The step called "Measured in flight" fits 5 constants
  again, starting from the answer.
- **R10, a hidden answer.** `gauges()` (line 191) reports the apogee and
  the perigee, the high point and the low point of the orbit. The
  world's own `orbit()` function computes them. The goal is "apogee =
  perigee = 200 km." So the pilot reads its score straight from the
  world, and the package never wrote this gauge down as a given.
- **R5, a separate scorer.** `orbit_error()` (line 310) is a loss
  function the author made by hand: a formula that turns the gap from
  the goal into one number to minimize. `plan()` (lines 337-367) tries
  every combination of a set of schedule values the author picked by
  hand, a grid search, and keeps the one with the lowest number. The
  author wrote `throttle_rule()` and `cutoff_rule()` too. The program
  did not find them.
- **R9, the claim.** The claim "Inserts into orbit within a few km of
  what it predicted" describes a simulator. The simulator agrees with a
  world made from the same equations and the same constants. The record
  shows that the pilot copied. It does not show that the pilot learned.
- **The goal.** The AGC is not in the loop at all. `pilot.py` flies
  `fly.World`, a toy world written in Python. The author recorded the
  real flight computer and then did not use the recording.

### fly.py

- **R10, a hidden answer.** `calibrate()` (lines 294-325) computes the
  pitch schedule, the launch window, the lead angles, and the deorbit
  point from the true physics constants, and writes those values into
  the plan's targets. The learner's score is then how close it gets to
  those targets. The plan is the answer, and the package does not say
  so.
- **R5, a separate scorer.** `Learner.cost()` is a weighted squared
  error against the targets. The author picked the weights and the
  tolerance for each instrument by hand. The learner picks whichever
  action it predicts will have the lowest cost. That is a training step
  for flying.
- **R2.** `LABELS` tells the learner which switch each button sets. A
  small given, but a given.
- **The goal.** There is no AGC here. The log entry for 10-10, late,
  lists 5 reasons the run failed. They are reasons a controller driven
  by a reward fails. They are not reasons Discovery fails, because the
  package never ran Discovery.

### room.py / lookback.py

These scripts are the closest to the spirit of the rules: they compare,
they loop, and they keep a memory. But they break these rules:

- **R6 and R7, a filter at the front.** `unexpected()` (line 84) keeps an
  overlap only if data in random order would reach the same overlap
  less than one time in 20. That filter throws out the common overlaps
  and the weak ones before they can interact with anything.
- **R3, deletion.** The retire step: if the dictionary refuses the words
  an overlap made 3 times, the overlap "stops being used." The log says
  cycle 3 got worse and the author added the retire step to fix it. R6
  says that is the wrong direction. The retire step is a correction for
  a problem the first filter caused.
- **R10, a hidden answer.** The "world" is a dictionary of the same root
  families the starting roots came from. The author confirmed the "13
  real words built" by asking that world. The world is an answer key,
  and the author built it from the answer. An answer key is allowed if
  the author says it's there. The docstring (the comment block at the
  top of the file) does say so, so the world is a declared given. That
  is permitted. But the author has to count it as a given.
- **R2, small.** The feature is letter triples, and the author merged
  `sh` and `kh` into single letters. That is knowledge of the language,
  handed to the program.
- **lookback.py, R3 again.** To mint is Discovery's word for making a
  new part out of two parts that share a start or an end. This script
  mints its own "filters": it makes them from the signal, out of the
  paths of tries that got a yes and tries that got a no, and then does
  not make a word when one of those filters applies. A filter the script
  makes from the signal is closer to the rules than one the author
  writes by hand. But it still removes. The rules say sort, don't skip:
  make the word, record the no, and keep both.

### effects.py, decisions.py, schedule.py

- **R2, a feature list.** `change_fact()` and `where_fact()` (lines
  67-85) list the kinds of change to look for: "up one," "down one," "to
  zero," "from zero," "tail10 matches." They say what an effect looks
  like before the search for effects starts. "tail10 matches" (the last
  10 bits agree) is knowledge that the AGC keeps its address in a 10-bit
  field.
- **R6, thresholds.** The cutoffs are: a change has to appear 90 percent
  of the time to count as a signature (a pattern that identifies a
  routine), groups need 3 or more members, and a 100 ms window before
  each jet firing. Each one is a cutoff that decides what counts.
- **R8, correct.** The scripts use names only when printing. That is
  right.

These scripts are fine as aids for reading the traces. They are not
Discovery, and they should not be presented beside Discovery as if they
were.

## 5. Givens: which were allowed, which were stated, and which were the answer

A given is allowed when it meets three conditions:

- (a) The author writes it down as a given.
- (b) It is the smallest thing that unblocks the work.
- (c) It is not the answer.

Discovery itself has three givens: the separator rule (cut the file at
its most common unit), the frame rule (pick the unit width with the
widest spread between its most constant and least constant column), and
the cap (a size limit on the pool of parts). `notes/design-rules.md`
now lists all three as givens.

| given | where | written down? | the smallest? | the answer? |
|---|---|---|---|---|
| the goal state (an orbit at 200 km, or "landed") | pilot.py `WAYPOINT`, fly.py plan | partly | yes | no. The goal state is R10's selection signal, and R10 allows it. |
| a flight plan (the shape of the trajectory: up, tip over, separate the stages, burn until the orbit gauges read the target) | pilot.py `PLAN`, fly.py `make_plan()` | yes, in the docstring | no. See below. | partly |
| the physics as equations | pilot.py `Model.predict()` | the package calls it "the manual" | no | **yes** |
| the true constants | pilot.py `PRIORS` | the package calls them "the plan's numbers" | no | **yes** |
| the apogee and perigee gauges that the world computes | pilot.py `gauges()` | no | no | **yes** |
| a score function | pilot.py `orbit_error()`, fly.py `cost()` | no | no | **yes**. A score function is the idea of right and wrong that R2 forbids. |
| plan targets worked out from the true constants | fly.py `calibrate()` | no | no | **yes** |
| panel labels (which switch each button sets) | fly.py `LABELS` | yes | yes | no |
| an oracle dictionary | room.py `WORLD` | yes | yes | it is the answer key. The author declared it, so R10 allows it. |
| letter triples, with `sh`/`kh` as single letters | room.py | yes | not certain | no |

**The flight plan concession.** A flight plan can be a given. What
matters is the form it takes. The Apollo crew's flight plan was a list
of DSKY entries and the time to make each one. The DSKY is the
spacecraft's keyboard and display, so a DSKY entry is a key press. A
plan like that is a procedure, not physics.

A concession in that form would be: "here are the programs in order:
P63, P64, P66; start each when the display shows the previous one is
done." (P63, P64 and P66 are the flight computer's numbered programs for
the landing.) That unblocks the key-press problem and gives away no
physics, no constants, and no scores. Instead, the package handed over
the mission-control side of the plan, which has three things in it: the
numbers the plan is built from, the equations behind those numbers, and
the gauges that report the result. That is the answer in the shape of a
plan.

If you want a clean list of concessions for this experiment, it is:

1. The goal row: the readings a landing shows. (R10 allows it.)
2. The DSKY key vocabulary. Or let the program find the vocabulary
   itself from OPR ERR, the error the computer shows when you press the
   wrong keys. Both are allowed, and the second costs little.
3. Optionally, the order of the programs as the crew had it. Say it's a
   given.

Nothing else. No physics, no constants, no gauges the world computes
from its internal values, and no cost function.

## 6. The method to follow

The author wrote this method down on the morning of 10-10, in chat and
in `notes/open.md` under "The AGC in the loop." This section states it
again, with what each step produces and what you must never hand the
program.

**Step 0. The code as a file.** Done, in `examples/agc/`. Discovery
read the flight program as a file and found the word size, the
instruction vocabulary, and `TC BANKCALL` with its targets. The author
gave it nothing.

**Step 1. Opcodes by effect.** The signal is the write trace: the
emulator's recording of every write the flight program makes to memory,
one record per write, holding the instruction word, the address, the
old value, and the new value. Run `discovery.py` on it. The mint groups
the records that share structure, and the classes (groups of parts that
take the same changes) sort the instruction words by the changes they
make. Writers, counters, flags, and the opcode bits (the part of an
instruction that says what to do) that decide each come out as classes.
If they don't, that absence is a result, and the record shows it. The
author gives nothing: no "up one," no "tail matches," no threshold.

**Step 2. What each subroutine reads and writes.** A subroutine is a
block of code that does one job. Cut the trace at the subroutine
boundaries that the step-0 record already found; to cut is to divide a
signal into runs at a separator. The write set of each stretch is the
addresses it wrote. The read set is the addresses it loaded before each
branch, and that comes from the instruction words once step 1 has
grouped the loads and the branches. Match the read set of one routine
against the write set of every other routine. That match is the
comparator on two sets, exactly as `bridge.py` does it. The order the
routines have to run in comes out of what each one needs. The author
gives nothing.

**Step 3. The code against the vehicle.** The signal is the three
recordings from one flight, all on the same clock: `writes.bin` (the
memory writes), `channels.bin` (the packets on the channels, the
numbered signal paths between the computer and its hardware), and
`vehicle.bin` (the vehicle's readings). Run Discovery on each one. Then
bridge the three records: find what they share. The bridge finds the
cells of the erasable memory (the memory the program can change), the
channel bits, and the vehicle rows that share structure. The vehicle
(`vehicle.py`) is the simulation, and it is allowed to know physics. The
learner never looks inside it. The author gives nothing except the
simulation.

**Step 4. The walk backward.** The given is the goal row (R10). From the
goal row, find the channel states that go with motion toward it. Then
find the routines that write those channels. Then the routines those
routines need. Then the keys that start those routines. The walk is
many hops through the record, and each hop is the comparator asking "is
this the node I'm looking for". If the walk doesn't reach a key, the
record says where it stopped, and that point is the result.

**Step 5. Press the keys the walk found.** The script `channel.py`
presses them. The vehicle moves, or it doesn't. Record the result, and
compare the final readings with the goal row. The difference goes back
in as the next signal. No reward, no cost, and no new plan: the
comparison is the feedback (R5).

At no step does the author give:

- equations
- constants
- a simulator the learner can run
- gauges the world computes from its internal values
- a score function
- a feature list
- a threshold

These things make the method hard, and the rules allow it to stay hard:

- Step 1 may not give clean opcode classes on the first try. The record
  decides.
- Step 2 is not exact where the AGC uses indexed addressing, where the
  code works out an address while it runs instead of writing it down.
  The trace fills that gap.
- Step 4 may stop before it reaches a key. That stop is the result.

The answer fixes none of these. More signal, a different cut, or a
second separator fixes them, and the rules allow all three.

## 7. What to keep and what to remove

Keep:

- the clock patch
- `agctrace.py`
- `vehicle.py`
- `run_vehicle.sh`
- `channel.py`
- `build.sh`
- `run.sh`
- `symtab.py`/`names.txt` as a lens: names for the reader, never for
  the method
- the recordings
- the result of the flight with the hold: the autopilot caught the
  nudge, and the real flight code sensed it and answered it through the
  socket

Remove from the repository: `fly.py`, `pilot.py`, and their logs. They
are not Discovery, and a reader will think they are. If you want a
record of the attempt, keep them somewhere else.

Keep separate: `room.py` and `lookback.py` are their own experiment. If
you keep them, do three things:

1. Remove the chance cutoff and the retire step.
2. Keep everything, with its counts.
3. Run them again.

The thing to find out is whether cycle 3 settles down without the
checks.

Rewrite `effects.py`, `decisions.py`, and `schedule.py` as readers only,
and say so in their headers. Or replace the categories the author
designed with a Discovery run on the same records, and compare what each
one finds.

Then do step 1. The write trace exists. `discovery.py` exists. The run
is one line. The record will show whether the method works on this
signal.
